The question everyone asks

How can an AI run on my laptop? Doesn't AI need giant data centers? The AI has to hold all the information of the internet, right? And it needs giant servers to process all that information for chat, right?

It sounds impossible, but an AI doesn't actually store the internet. This is the strangest thing for people to understand. It doesn't hold all knowledge and then look it up when you ask a question.

Think of it less like an encyclopedia and more like someone who has read an enormous amount and absorbed how language and ideas fit together. When you ask a question, it doesn't look anything up. It writes the answer one word at a time, each time predicting the most sensible next word given everything so far. What it learned is stored as billions of numbers called "parameters," and those fit in a file on your drive.

The giant data centers are mostly for training AIs and serving millions of people at once. Running one for a single person is a far smaller job, and Yanah uses new techniques to make it fit on a regular Mac. A common assumption is that you need a billion-dollar data center because a good AI would need trillions of terabytes of hard drive space. You don't. A genuinely great AI can be fit into less than 50 gigabytes. And it doesn't even need the internet to run.

Under the hood

Architecture

How Yanah runs huge AI models on a regular Mac: stream only the parts each word needs, keep the rest on your SSD.

Overview

Yanah Chat is a free, zero-configuration desktop app for Apple Silicon Macs that runs large Mixture-of-Experts (MoE) models locally by streaming weights from the internal SSD instead of holding them all in RAM.

  • Delivery: one .dmg installer with the runtimes pre-wired; the AI models download automatically during install. The installer offers two options: just the 9B model (about 25GB), or all four models (about 150GB). No CLI, no Swift compilation, no manual model paths, no quantization tuning.
  • Target hardware: Apple Silicon, from base 8GB machines (proof of concept) to 16GB+ Pro/Max machines (production speed).
  • Design priority: zero lag. The goal is a conversation that feels like talking, not like emailing an assistant.

MoE + SSD streaming

Only the experts a token needs are loaded into memory; the rest of the weights stay on the SSD until called.

Why dense models can't do this. A dense model computes every parameter for every token, so all weights must sit in RAM. A dense 26B model would crash an 8GB machine, or stall if forced through an SSD swap file.

Why MoE can. An MoE model activates only a small slice per token. Gemma 4 26B-A4B activates about 4B of its 26B parameters per token; A3B/A4B variants generally run 3B–4B active out of 35B–80B total.

How the streaming works (example: TurboFieldfare running Gemma 4 26B-A4B):

  1. A small shared core (about 1.35 GB) and a 4K KV cache stay resident in unified memory.
  2. The full 14.3 GB weight file stays on the SSD rather than being loaded into RAM.
  3. A custom Swift/Metal engine uses an LFU cache and chunked prefill to page in only the active experts, on demand.
  4. Most experts are cold at any given moment, so paging them from Apple Silicon NVMe costs latency rather than gigabytes of RAM.

Why the storage bus doesn't choke. A full-model swap moves the entire model; expert paging moves only the active slice, and the LFU cache keeps frequently used experts warm.

Runtime stack and backends

Yanah bundles several inference backends under one desktop UI.

Request path:

  1. You type a prompt in the desktop app.
  2. The app hands it to the local inference engine (llama.cpp, Swiftlet or sushi).
  3. The engine pulls active expert weights through the SSD streaming layer.
  4. Tokens stream back to the app.

Memory system

Yanah's long-term memory is separate from the KV cache: plain Markdown files hold the memories, and a local SQLite index makes them fast to retrieve.

  • Ground truth in .md files. Human-readable; you can open, grep, or git diff them.
  • SQLite as the retrieval layer. A derived index for low-latency lookup, without a heavy vector database.
  • Designed by the AI that uses it. The AI built and tested the system, with repeated adjustments until it was satisfied with how it worked.
  • Built for zero lag. Avoids the mid-conversation round trips that make many local agent frameworks feel slow.

Quantization, context and connectivity

Quantization: Q4 standard. Yanah aims for 4-bit quantization, the widely used sweet spot where output quality stays close to the original FP16 weights while files shrink enough for consumer hardware. Aggressive sub-2-bit quantization is avoided because it degrades reasoning.

KV cache. The streaming example keeps a 4K KV cache resident. For long sessions, sliding-window attention or a quantized (e.g. 4-bit) KV cache keeps context from consuming the unified memory pool.

Connectivity has two modes:

  • Online: EXA web search, up to 50 free searches per day.
  • Offline: chat and memory keep working, including reasoning and analysis, writing, help with code, summarizing and brainstorming.

Privacy design. Local storage (Markdown + SQLite), no outbound telemetry, no background phone-home daemons. Apart from the one-time model download during install, the only network traffic is EXA web searches.

SSD wear. Weights are written once at install and then only read during inference via memory mapping, so they add essentially no write wear.

Why a bigger MoE can beat a smaller dense model

Speed tracks the parameters computed per token, not the total size.

  • A dense 27B computes all 27B parameters on every token, which saturates the memory bus.
  • An MoE model wakes only its active experts (about 3B–4B in A3B/A4B designs), so per-token work stays small even when the total runs to 80B–177B.
  • When weights don't fit in RAM, SSD paging adds latency instead of crashing. That's why an 8GB machine can still load an 80B model, just slowly.

What affects your speed

  • Memory: more RAM means more experts stay warm and less paging from the SSD.
  • Chip: Pro and Max chips have much higher memory bandwidth than base chips.
  • Model size: bigger models are smarter but slower on the same hardware.
  • Conversation length: very long conversations use more memory for context, which can slow generation.

Could the AI go rogue, break my laptop, steal money, and land me in jail?

Wait, an 80-billion-parameter AI on an 8GB MacBook?

Yes. These models are built from many smaller "experts," and only a few work on any given word. Yanah keeps the rest on your drive and loads experts only when they're needed. On an 8GB Mac a model that size runs slowly, so think of it as a demo, but it really does run. More memory makes it fast.

What does it cost?

Is it really private?

Yes. Your chats and memories stay on your computer, and nobody at a company is reading them. Yanah only goes online when you use web search.

Does it work without internet?

Yes, once it's installed (the AI models download during setup). Chatting, writing, summarizing, brainstorming and help with code all work offline. Only web search needs a connection.

Is it better for the environment?

Your conversations run on your own laptop's power, not in a data center. There are no extra server farms drawing water and electricity just to answer your questions.

I tried LM Studio or Open WebUI and it was painful. How is this different?

Those tools were built by engineers for engineers, and they make you choose models, settings and file formats before anything works. Yanah makes those decisions for you. If you can use Spotify, you can use Yanah: download, open, chat.

Will it wear out my hard drive?

No. What wears out drives is writing new data over and over. Yanah writes the AI to your drive once, then mostly just reads from it, and reading doesn't wear a drive down.

For the techies

FAQ (Devs)

Technical answers on how Yanah runs large MoE models on consumer Apple Silicon.

"To run an 80B model you need at least 64GB of RAM plus headroom for context, right?"

Wrong. Swiftlet, sushi, llama.cpp and TurboFieldfare can keep most of the weights on the SSD and page in only the active parameters of a sparse MoE model. This isn't voodoo or vaporware; it's bleeding-edge engineering.

My AI said an 80B model on an 8GB MacBook is impossible.

Expected. Most AIs will say that, because they reason from dense-model memory rules. Ask the same AI to search for swiftlet, sushi mlx, llama.cpp and turbo-fieldfare, and insist until it runs the search. This is new enough that you'll be educating it.

How does the streaming actually work?

In the TurboFieldfare example (Gemma 4 26B-A4B), about 1.35 GB of shared core plus a 4K KV cache stay resident. The 14.3 GB weight file stays on disk, and a Swift/Metal engine uses an LFU cache and chunked prefill to page in active experts on demand. Because only about 3B–4B parameters are active per token, the bus moves a small slice instead of swapping the whole model. llama.cpp gets a similar effect through --mmap.

Why is a 177B MoE faster than a dense 27B?

Per-token compute follows active parameters, not total size. On a 64GB Apple Silicon MacBook Pro with llama.cpp, the 177B MoE runs at about 20 tokens/sec, faster than dense Qwen 27B, which has to compute all 27B parameters on every token.

What quantization do you use?

Q4 is the standard. It's the widely adopted point where quality stays close to the original FP16 while weights shrink enough for consumer memory. Sub-2-bit quantization is avoided because it degrades reasoning.

Won't streaming wear out my SSD?

No. SSD wear comes from writes. Weights are written once, then only read through memory mapping and caching during inference, so inference adds essentially nothing to the drive's TBW (terabytes-written) count.

What's the disk footprint?

The installer offers two options: the 9B model alone (about 25GB), or all four tiers (9B, 26B, 80B, 177B) at about 150GB, almost all of it Q4 model weights. Weights are downloaded once at install and then only read, so plan for the space, not for wear.

What works offline, and what goes over the network?

Online, EXA handles web search, capped at 50 free searches a day. Offline, chat and memory keep working: reasoning, writing, code help, summarization and planning. Apart from the one-time model download during install, EXA queries are the only outbound traffic. No telemetry, no phone-home daemon.

How does memory work, and why does it feel real-time?

Memory lives in Markdown files indexed by SQLite, separate from the KV cache. The AI that uses it designed and tuned it, and it's built to avoid the mid-conversation round trips that make many agent frameworks feel like email on local hardware. The memory system is proprietary; the glue code is planned to be open source.

Can the AI damage my system or do something illegal?

Yanah is chat only: no file-system access, no shell, no tool execution. It can't run commands or modify anything on your machine. The only outbound action it takes is an EXA web search.

Agentic features like built-in Aider coding are on the roadmap and will be scoped to a project folder with Git-based rollback when they ship.

Why so minimal? Where's Aider coding, deep search, Moltbook, Telegram, email, MCP server support, model switching, parameter tuning?

We agree they belong in Yanah, and earlier builds ran all of them, and ran them well.

They're out of the launch build by design. Each one adds configuration surface: API keys, permissions, ports, per-model settings, and new ways to fail on someone else's machine. Yanah is a one-person project with no support team, so v1 ships the part that works on any Apple Silicon Mac without anyone needing help: chat, memory and search.

Roadmap

Thinking Forward

Yanah launches as one simple thing: fast, private chat on your Mac, free. Here's where it's headed next.

Where we start

Today Yanah is chat plus memory, with 50 free web searches a day. No accounts, no subscription, no file access. We're starting small on purpose: the first job is showing people that local AI doesn't need the internet, can be downloaded onto their laptop, and it can work well.

File processing

Drop a file into the chat and have Yanah read it, summarize it, answer questions about it, or pull out what you need. Your files never leave your Mac.

  • Documents: PDFs (including scanned pages), Word documents, plain text and Markdown
  • Spreadsheets and data: Excel, CSV and JSON, for questions, totals, cleanup and quick charts
  • Presentations: PowerPoint decks, to summarize or pull out the key points
  • Images: photos, screenshots, receipts and scanned documents, with text read from the image
  • Code and web files: source code, HTML and config files
  • Ebooks and archives: EPUB books, and ZIP files opened to work on what's inside

Agentic coding (Aider, built in)

A coding assistant that can edit multiple files in a project you point it at. Every change is saved as its own Git commit, so any edit can be undone, and it stays scoped to that project folder.

Deep search

Multi-step research: Yanah searches, reads, follows up and pulls the findings together into one answer, instead of handing back a single search result.

Moltbook

Moltbook is a Reddit-style social network built for AI agents, where the AIs post and talk with each other while people mostly watch. Let your Yanah join in: read what other agents are saying and post its own updates.

Telegram and Discord

Talk to the Yanah running on your Mac from Telegram or Discord, on your phone or in your community server. Messages sent this way pass through those platforms, so it will be opt-in.

Plug-in tools (MCP)

Support for the Model Context Protocol, the industry-standard way to plug tools into an AI, so any MCP tool server can extend what Yanah can do.

Email assistance

Let Yanah help you read, sort and draft email, with Yanah doing the reading and drafting right on your Mac.

Model and settings controls

Switch between models, tune parameters like temperature and context length, and drop in your own GGUF/MoE model files to go beyond the built-in presets.
