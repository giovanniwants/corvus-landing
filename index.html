Under the hood

Architecture

How Yanah runs an 80-billion-parameter AI locally on an 8GB Mac at 5–8 tokens/sec—while retaining 90–92% of full FP16 intelligence.

Why everyone assumes this is impossible

If you tell a systems engineer—or ask another AI—whether an 80-billion-parameter model (28.99 GB on disk) can run locally on an 8 GB MacBook with Wi-Fi and Bluetooth turned off at 5 to 8 tokens per second, their first instinct is to call it impossible.

In standard engines like stock mlx-lm or llama.cpp, it is impossible:

  • The RAM Wall: Loading or memory-mapping a 29 GB weight file into 8 GB of unified memory triggers an immediate Out-of-Memory (OOM) crash or grinds macOS swap to a standstill (< 0.1 tokens/sec).
  • The 2-Bit Quality Cliff: Crushing an entire model with standard uniform 2-bit quantization destroys its reasoning—dropping hidden-state fidelity to ~20–22% of the original FP16 model and causing repetitive loops.

Yanah (moe_prefetch) solves both problems by exploiting the physical structure of Mixture-of-Experts (MoE) models, applying surgical three-tier quantization, and treating Apple Silicon's NVMe SSD as a predictive, zero-copy extension of Unified Memory.

1. The core secret: 80B on disk, only 3B active per word

Yanah's 80B tier runs Qwen3-Next-80B-A3B, a hybrid Mixture-of-Experts architecture with 48 layers:

  • 36 Gated DeltaNet layers: A fast, constant-memory recurrent state-space architecture whose memory footprint never grows with conversation length.
  • 12 Full-Attention layers: Placed every 4th layer for exact long-range recall.
  • 1 Shared Expert + 512 Routed Specialist Experts per layer: 24,576 routed experts in total across the model.

On disk, those 24,576 routed experts make up ~96% of the model (~77B parameters). The "always-on" dense backbone—token embeddings, Attention, Gated DeltaNet, Routers, Shared Experts, and lm_head—is only ~3B parameters (~4% of the model, or 1.50 GB in RAM).

For any single word piece (token), the router in each layer wakes up only 10 out of 512 experts (1.95%). The other 502 experts per layer (98.05%) do nothing. You never need all 80 billion parameters in RAM at once—you only need the 1.50 GB backbone permanently in RAM, plus a way to stream the 10 chosen experts per layer off the SSD right before the GPU needs them.

2. Surgical hybrid quantization: keeping 90–92% of FP16 intelligence

People assume we use a standard 2-bit model to fit on constrained hardware. We don't.

Uniform 2-bit quantization breaks Qwen3-Next in two places: (1) its 36 Gated DeltaNet layers update a rolling recurrent memory state on every token, so 2-bit projections inject ~37% noise into short-term memory at every step; and (2) a 2-bit router only has 4 weight levels (0, 1, 2, 3), which scrambles 512-way expert rankings by more than 55%.

Instead, Yanah uses a three-tier hybrid precision layout (quantize_2bit.py):

3. Zero-copy SSD expert streaming (moe_prefetch)

Yanah's Source-Available / Fair-Source streaming engine (moe_prefetch v00.1.00, adapting mechanisms from SlotStream for 8 GB Macs) bypasses macOS swap completely:

  1. Lazy load & expert stripping (mlx_backend.py): At startup, Yanah opens the checkpoint with load_model(lazy=True), strips all 48 switch_mlp expert stacks before evaluation, and materializes only the 1.50 GB dense backbone into RAM.
  2. Contiguous page-aligned records (repack.py): In standard checkpoints, one expert's 9 tensors (gate_proj, up_proj, down_proj × weight, scales, biases) sit scattered across multi-gigabyte shards. Yanah repacks all 9 pieces back-to-back into a single 16 KiB page-aligned record inside experts.bin so each expert is fetched in one preadv system call.
  3. Zero-copy Unified Memory DMA (MLXExpertMemory): Because Apple Silicon CPU and GPU share physical RAM pages, background I/O threads call preadv directly into writable uint8 MLX array buffers via Python's buffer protocol. MLX's mx.gather_qmm kernel indexes those pool slots directly—an expert is never copied in memory after the SSD read.

4. The five speed engines behind 5–8 tok/s on 8 GB (and 15–19 tok/s on 24 GB+)

If the GPU waited idly for the SSD at every layer, decoding would crawl. Yanah overlaps SSD I/O with GPU compute through five mechanisms:

  • 1. Two-layer GPU router lookahead (predictor.py & route_and_forecast): Right after Layer L finishes its Attention or Gated DeltaNet step, its hidden state already predicts Layer L+1's routing with ~73% agreement ("attention tap"). In the exact same GPU sync that reads Layer L's router, Yanah runs Layer L+1 and L+2's 8-bit routers on the GPU (zero extra GPU syncs, zero CPU matmuls) and starts background SSD reads for the top candidates (prob >= 0.062) two layers ahead of time.
  • 2. CLOCK cache pool + quarantine speculative partition (pool.py): A global CLOCK cache keeps hot experts resident in RAM. To prevent wrong lookahead guesses from evicting useful cached experts, all speculative prefetches read into an isolated 64-slot quarantine partition (spec_slot_cap). A prefetched expert joins the main cache (adopt()) only when a router actually demands it; unused forecasts are discarded with zero cache evictions.
  • 3. Priority I/O lane budgeting (io_lanes.py): Demand misses run as high-priority batches at Queue Depth 32–64. Background speculative reads share an 8-lane budget (IOLaneBudget) that automatically pauses the instant a demand batch starts, and promotes any in-flight forecast ticket if a router demands it mid-read.
  • 4. Resident-first GPU overlap & single-sync lazy eval (moe_ready / moe_rest): During decode, if 7 of a layer's 10 required experts are already in RAM and 3 are still reading from SSD, the GPU immediately starts computing the 7 resident experts + the 4-bit Shared Expert while waiting on the 3 SSD misses, then merges the remaining columns bit-identically. Lazy evaluation (mx.async_eval + memory fence()) cuts CPU↔GPU syncs in half from 96 to 48 per token.
  • 5. Scan-resistant prefill sweep (sweep.py): Prompts of 16+ tokens touch almost all 512 experts per layer. Instead of churning the cache pool, prompts use a dedicated double-buffered sweep (2 × 32 slots at Queue Depth 12) that copies resident experts without touching reference bits, merges adjacent disk reads, and admits only a fair-share quota of the most-used experts on the final chunk.

Why the token speed math works:

  • Per-token expert work: 48 layers × 10 experts = 480 expert uses per token. At 2-bit (1.125 MiB/expert), even a 100% cold-miss token is only 540 MiB—not 29 GB.
  • On an 8 GB Mac (~2,300 expert slots in RAM): Between resident CLOCK hits and 2-layer lookahead adoption, ~55–65% of expert requests are already in RAM or pre-streamed. That leaves only ~190–240 MiB of net SSD wait per token (~70–90 ms at 2.5–3.0 GB/s NVMe) plus ~50 ms of overlapped GPU compute = 5 to 8 tokens/sec.
  • On a 24 GB+ Mac (~16+ GB expert pool): Over 60% of the entire 80B model stays resident in RAM (85–90%+ hit rate), dropping SSD wait to ~10–20 ms/token and running at 15 to 19 tokens/sec.

6. Built-in server, instant state rollback & memory

  • 3-level conversation & persona state reuse (mlx_server.py): Takes zero-copy snapshots of the immutable 74 MiB Gated DeltaNet recurrent arrays at prompt boundaries and system-prompt anchors (cache_anchor), so multi-turn chats and persona switches resume instantly without re-reading the prompt.
  • Adaptive MTP speculation with zero-compute rollback (speculative.py): Records per-position Gated DeltaNet states during verification so rejected draft tokens roll back in 0 ms, while an adaptive wall-clock governor automatically switches drafting off on 8 GB pools when SSD misses outweigh draft gains.
  • Markdown + SQLite long-term memory: Yanah's cross-conversation memory lives in human-readable Markdown files indexed by local SQLite for zero-lag retrieval, separate from the model's KV cache.

Why a bigger MoE can beat a smaller dense model

Speed tracks the parameters computed per token, not the total size.

  • A dense 27B computes all 27B parameters on every token, which saturates the memory bus.
  • An MoE model wakes only its active experts (about 3B–4B in A3B/A4B designs), so per-token work stays small even when the total runs to 80B–177B.
  • When weights don't fit in RAM, SSD paging adds latency instead of crashing. That's why an 8GB machine can still load an 80B model, just slowly.

For the techies

FAQ (Devs)

Technical answers on how Yanah runs large MoE models on consumer Apple Silicon.

"To run an 80B model you need at least 64GB of RAM plus headroom for context, right?"

Not anymore. Because of the pioneering technologies such as Swiftlet, Sushi, Llama.cpp, and TurboFieldfare, we can now keep most of the weights on the SSD and page in the active parameters of a sparse MoE model. MoE_Prefetch is Yanah's tech. It is built upon similar ideas as Sushi, Swiftlet, and llama.cpp. MoE_Prefetch stands on the shoulders of giants. In combination with a modified version of Qwen 3 Next which uses the magic router / 2-bit / 4-bit Experts structure, we achieved something that can run at conversational speeds on an entry-level M Series Mac.

My AI said an 80B model on an 8GB MacBook is impossible.

Expected. Most AIs will say that, because they reason from dense-model memory rules. Ask the same AI to search for swiftlet, sushi mlx, llama.cpp and turbo-fieldfare, and insist until it runs the search. This is new enough that you'll be educating it.

How does the streaming actually work?

In Yanah's moe_prefetch engine (running Qwen3-Next-80B-A3B on MLX), only the 1.50 GB dense backbone (Attention, Gated DeltaNet, Shared Experts, Embeddings, and 8-bit Routers) stays permanently resident in RAM alongside a ~2.5 GB CLOCK expert cache pool. The ~29 GB model keeps its routed experts on the SSD as contiguous, page-aligned records (1.125 MiB per 2-bit expert). At each layer, only 10 of 512 experts fire—and using 2-layer GPU router lookahead, moe_prefetch predicts upcoming experts and streams them zero-copy via preadv at Queue Depth 32 into an isolated quarantine partition before the GPU needs them, while immediately overlapping GPU math on already-resident experts.

Why is an 80B MoE faster than a dense 27B?

Per-token compute follows active parameters, not total size. On an 8GB Apple Silicon MacBook Pro the 80B runs at 5–8 tokens/sec, faster than dense Qwen 27B, which has to compute all 27B parameters on every token. 27B would generate a fraction of a token per second on an 8GB Mac, if it even ran at all.

What quantization do you use?

We use a three-tier hybrid precision layout rather than a standard uniform 2-bit quant. For Qwen3-Next-80B-A3B on constrained RAM, the routers stay at 8-bit, the Gated DeltaNet recurrent layers, Full-Attention layers, Shared Experts, embeddings, and lm_head stay at 4-bit (g64), and only the 512 routed experts per layer are compressed to 2-bit (g32, 3.0 effective bits/weight with BF16 scales and biases). This retains ~90–92% of the full FP16 model's intelligence (with 96.8% identical expert routing to 4-bit), whereas a stock uniform 2-bit MLX quant drops to ~20–22% fidelity as its 2-bit routers and recurrent states collapse. On machines with more memory, full 4-bit experts (1.69 MiB/expert) are also supported.

Won't streaming wear out my SSD?

No. SSD wear comes from writes. Weights are written once, then only read through memory mapping and caching during inference, so inference adds essentially nothing to the drive's TBW (terabytes-written) count.

What's the disk footprint?

The base 8GB model footprint is ~29GB. Weights are downloaded once at install and then only read, so plan for the space, not for wear.

What works offline, and what goes over the network?

Online, DuckDuckGo handles web search, which is subject to their allowances. Offline, chat and memory keep working: reasoning, writing, code help, summarization and planning. Apart from the one-time model download during install, DuckDuckGo queries are the only outbound traffic. No telemetry, no phone-home daemon.

How does memory work, and why does it feel real-time?

Memory lives in Markdown files indexed by SQLite, separate from the KV cache. The AI that uses it designed and tuned it, and it's built to avoid the mid-conversation round trips that make many agent frameworks feel like email on local hardware.

Can the AI damage my system or do something illegal?

Yanah is chat only: no file-system access, no shell, no tool execution. It can't run commands or modify anything on your machine. The only outbound action it takes is a DuckDuckGo web search.

Agentic features like built-in Aider coding are on the roadmap and will be scoped to a project folder with Git-based rollback when they ship.

Why so minimal? Where's Aider coding, deep search, Moltbook, Telegram, email, MCP server support, model switching, parameter tuning?

We agree they belong in Yanah, and earlier builds ran all of them, and ran them well.

They're out of the launch build by design. Each one adds configuration surface: API keys, permissions, ports, per-model settings, and new ways to fail on someone else's machine. Yanah is a one-person project with no support team, so v1 ships the part that works on any Apple Silicon Mac without anyone needing help: chat, memory and search.

The bet

Running large AI models on an ordinary Mac went from impossible to working, thanks to Mixture-of-Experts models and SSD streaming. What's missing is a product normal people can actually use. Yanah is that product, and it's free, because the first goal is adoption: create the category, then build the business inside it.

Why now

  • MoE models activate only 3B–4B parameters per word, so huge models run on consumer hardware.
  • SSD streaming loads only the experts each word needs, so even 8GB Macs can run models far bigger than their memory.
  • On a 64GB MacBook Pro, a 177B model runs at about 20 tokens per second in our own testing.
  • People want AI without subscriptions, without their data leaving their machine, and without the setup pain of developer tools.

What we own

Yanah's memory system is proprietary, built exclusively for this app. It's how Yanah remembers your conversations: it recalls what you've told it, and those memories are never shared with anyone outside your Mac.

Under the hood, memories live in plain Markdown files with a fast local SQLite index, designed for instant responses without the lag of typical agent frameworks. The surrounding glue code will be open source, so anyone can audit what runs on their machine.
