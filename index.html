The question everyone asks

Big AI. No cloud. Free.

How can an AI run on my laptop? Doesn't AI need giant data centers?

It sounds impossible, but an AI doesn't actually store the internet. This is the strangest thing for people to understand. It doesn't hold all knowledge and then look it up when you ask a question.

Think of it less like an encyclopedia and more like someone who has read an enormous amount and absorbed how language and ideas fit together. When you ask a question, it doesn't look anything up. It writes the answer one word at a time, each time predicting the most sensible next word given everything so far. What it learned is stored as billions of numbers called "parameters," and those fit in a file on your drive.

The giant data centers are mostly for training AIs and serving millions of people at once. Running one for a single person is a far smaller job, and Yanah uses new techniques to make it fit on a regular Mac. A genuinely great AI can be fit into less than 50 gigabytes. And it doesn't even need the internet to run.

FAQ (Everyone)

Straight answers about Yanah, the free, private AI that runs on your Mac.

Could the AI go rogue, break my laptop, steal money, and land me in jail?

No. Yanah is a chat window. It can't touch your files, open your bank, install anything, or do anything on its own. It only replies to what you type. The one thing it can reach out for is a web search, and only when you use one.

Wait, an 80-billion-parameter AI on an 8GB MacBook?

Yes. These models are built from many smaller "experts," and only a few work on any given word. Yanah keeps the rest on your drive and loads experts only when they're needed. This results in conversational speed (5–8 tokens/sec) on an 8GB Mac.

What does it cost?

Nothing. Yanah Chat is completely free: every model, no subscription.

Is it really private?

Yes. Your chats and memories stay on your computer, and nobody at a company is reading them. Yanah only goes online when you use web search.

Does it work without internet?

Yes, once it's installed (the AI models download during setup). Chatting, writing, summarizing, brainstorming and help with code all work offline. Only web search needs a connection.

Is it better for the environment?

Your conversations run on your own laptop's power, not in a data center. There are no extra server farms drawing water and electricity just to answer your questions.

I tried LM Studio or Open WebUI and it was painful. How is this different?

Those tools were built by engineers for engineers, and they make you choose models, settings and file formats before anything works. Yanah makes those decisions for you. If you can use Spotify, you can use Yanah: download, open, chat.

I asked ChatGPT, Claude or Gemini and it said this is impossible.

That's expected. This technology is so new that most AIs still go by the old rules. Ask the same AI to search the web for "swiftlet," "sushi mlx," "llama.cpp" and "turbo-fieldfare," and insist until it actually runs the search. You'll be the one teaching it.

Will it wear out my hard drive?

No. What wears out drives is writing new data over and over. Yanah writes the AI to your drive once, then mostly just reads from it, and reading doesn't wear a drive down.

How much space does it need?

The base model for Macs from 8GB to 36GB of RAM is less than 30GB. The 177B model for 48GB+ Macs could be up to 150GB, because the bigger AI models are very large files.

Before installing, check your free space under Apple menu → System Settings → General → Storage, and download over fast Wi-Fi. The full install will take a while.

How fast will it be on my Mac?

It depends on how much memory your Mac has and which model you pick. More memory means faster answers. See the Performance section for real examples.

Why is Yanah so simple? It would be great if it had coding, deep search, Moltbook, Telegram, email, plug-in tools, or let me change models and settings.

We agree, and Yanah can do all of that. Earlier versions already ran these features, and ran them well.

We left them out of the launch on purpose. Every extra feature is one more thing that can break or need setting up on your computer, and Yanah is built by one person, without a support team behind it. So the first version does a few things and does them reliably: anyone can install it and start chatting with no help. Your grandma included.

Why a bigger MoE can beat a smaller dense model

Speed tracks the parameters computed per token, not the total size.

A dense 27B computes all 27B parameters on every token, which saturates the memory bus. An MoE model wakes only its active experts (about 3B–4B in A3B/A4B designs), so per-token work stays small even when the total runs to 80B–177B.

When weights don't fit in RAM, SSD paging adds latency instead of crashing. That's why an 8GB machine can still load an 80B model, just slowly.

What affects your speed

  • Memory: more RAM means more experts stay warm and less paging from the SSD.
  • Chip: Pro and Max chips have much higher memory bandwidth than base chips.
  • Model size: bigger models are smarter but slower on the same hardware.
  • Conversation length: very long conversations use more memory for context, which can slow generation.

Architecture

How Yanah runs an 80-billion-parameter AI locally on an 8GB Mac.

How Yanah runs an 80-billion-parameter AI locally on an 8GB Mac at 5–8 tokens/sec—while retaining 90–92% of full FP16 intelligence.

Why everyone assumes this is impossible

If you tell a systems engineer—or ask another AI—whether an 80-billion-parameter model (28.99 GB on disk) can run locally on an 8 GB MacBook with Wi-Fi and Bluetooth turned off at 5 to 8 tokens per second, their first instinct is to call it impossible.

In standard engines like stock mlx-lm or llama.cpp, it is impossible:

  • The RAM Wall: Loading or memory-mapping a 29 GB weight file into 8 GB of unified memory triggers an immediate Out-of-Memory (OOM) crash or grinds macOS swap to a standstill (< 0.1 tokens/sec).
  • The 2-Bit Quality Cliff: Crushing an entire model with standard uniform 2-bit quantization destroys its reasoning—dropping hidden-state fidelity to ~20–22% of the original FP16 model and causing repetitive loops.

Yanah (moe_prefetch) solves both problems by exploiting the physical structure of Mixture-of-Experts (MoE) models, applying surgical three-tier quantization, and treating Apple Silicon's NVMe SSD as a predictive, zero-copy extension of Unified Memory.

The core secret: 80B on disk, only 3B active per word

Yanah's 80B tier runs Qwen3-Next-80B-A3B, a hybrid Mixture-of-Experts architecture with 48 layers:

  • 36 Gated DeltaNet layers: A fast, constant-memory recurrent state-space architecture whose memory footprint never grows with conversation length.
  • 12 Full-Attention layers: Placed every 4th layer for exact long-range recall.
  • 1 Shared Expert + 512 Routed Specialist Experts per layer: 24,576 routed experts in total across the model.

On disk, those 24,576 routed experts make up ~96% of the model (~77B parameters). The "always-on" dense backbone—token embeddings, Attention, Gated DeltaNet, Routers, Shared Experts, and lm_head—is only ~3B parameters (~4% of the model, or 1.50 GB in RAM).

For any single word piece (token), the router in each layer wakes up only 10 out of 512 experts (1.95%). The other 502 experts per layer (98.05%) do nothing. You never need all 80 billion parameters in RAM at once—you only need the 1.50 GB backbone permanently in RAM, plus a way to stream the 10 chosen experts per layer off the SSD right before the GPU needs them.

Surgical hybrid quantization: keeping 90–92% of FP16 intelligence

People assume we use a standard 2-bit model to fit on constrained hardware. We don't.

Uniform 2-bit quantization breaks Qwen3-Next in two places: (1) its 36 Gated DeltaNet layers update a rolling recurrent memory state on every token, so 2-bit projections inject ~37% noise into short-term memory at every step; and (2) a 2-bit router only has 4 weight levels (0, 1, 2, 3), which scrambles 512-way expert rankings by more than 55%.

Instead, Yanah uses a three-tier hybrid precision layout (quantize_2bit.py):

And because 10 routed experts are weighted and summed on top of the 4-bit Shared Expert at every layer, uncorrelated quantization noise across the 10 experts partially cancels out.

Zero-copy SSD expert streaming (moe_prefetch)

Yanah's Source-Available / Fair-Source streaming engine (moe_prefetch v00.1.00, adapting mechanisms from SlotStream for 8 GB Macs) bypasses macOS swap completely:

  • Lazy load & expert stripping (mlx_backend.py): At startup, Yanah opens the checkpoint with load_model(lazy=True), strips all 48 switch_mlp expert stacks before evaluation, and materializes only the 1.50 GB dense backbone into RAM.
  • Contiguous page-aligned records (repack.py): In standard checkpoints, one expert's 9 tensors (gate_proj, up_proj, down_proj × weight, scales, biases) sit scattered across multi-gigabyte shards. Yanah repacks all 9 pieces back-to-back into a single 16 KiB page-aligned record inside experts.bin so each expert is fetched in one preadv system call.
  • Zero-copy Unified Memory DMA (MLXExpertMemory): Because Apple Silicon CPU and GPU share physical RAM pages, background I/O threads call preadv directly into writable uint8 MLX array buffers via Python's buffer protocol. MLX's mx.gather_qmm kernel indexes those pool slots directly—an expert is never copied in memory after the SSD read.
The five speed engines behind 5–8 tok/s on 8 GB (and 15–19 tok/s on 24 GB+)

If the GPU waited idly for the SSD at every layer, decoding would crawl. Yanah overlaps SSD I/O with GPU compute through five mechanisms:

  • 1. Two-layer GPU router lookahead (predictor.py & route_and_forecast): Right after Layer L finishes its Attention or Gated DeltaNet step, its hidden state already predicts Layer L+1's routing with ~73% agreement ("attention tap"). In the exact same GPU sync that reads Layer L's router, Yanah runs Layer L+1 and L+2's 8-bit routers on the GPU (zero extra GPU syncs, zero CPU matmuls) and starts background SSD reads for the top candidates (prob >= 0.062) two layers ahead of time.
  • 2. CLOCK cache pool + quarantine speculative partition (pool.py): A global CLOCK cache keeps hot experts resident in RAM. To prevent wrong lookahead guesses from evicting useful cached experts, all speculative prefetches read into an isolated 64-slot quarantine partition (spec_slot_cap). A prefetched expert joins the main cache (adopt()) only when a router actually demands it; unused forecasts are discarded with zero cache evictions.
  • 3. Priority I/O lane budgeting (io_lanes.py): Demand misses run as high-priority batches at Queue Depth 32–64. Background speculative reads share an 8-lane budget (IOLaneBudget) that automatically pauses the instant a demand batch starts, and promotes any in-flight forecast ticket if a router demands it mid-read.
  • 4. Resident-first GPU overlap & single-sync lazy eval (moe_ready / moe_rest): During decode, if 7 of a layer's 10 required experts are already in RAM and 3 are still reading from SSD, the GPU immediately starts computing the 7 resident experts + the 4-bit Shared Expert while waiting on the 3 SSD misses, then merges the remaining columns bit-identically. Lazy evaluation (mx.async_eval + memory fence()) cuts CPU↔GPU syncs in half from 96 to 48 per token.
  • 5. Scan-resistant prefill sweep (sweep.py): Prompts of 16+ tokens touch almost all 512 experts per layer. Instead of churning the cache pool, prompts use a dedicated double-buffered sweep (2 × 32 slots at Queue Depth 12) that copies resident experts without touching reference bits, merges adjacent disk reads, and admits only a fair-share quota of the most-used experts on the final chunk.

For the techies

FAQ (Devs)

Technical answers on how Yanah runs large MoE models on consumer Apple Silicon.

"To run an 80B model you need at least 64GB of RAM plus headroom for context, right?"

Not anymore. Because of the pioneering technologies such as Swiftlet, Sushi, Llama.cpp, and TurboFieldfare, we can now keep most of the weights on the SSD and page in the active parameters of a sparse MoE model. MoE_Prefetch is Yanah's tech. It is built upon similar ideas as Sushi, Swiftlet, and llama.cpp. MoE_Prefetch stands on the shoulders of giants. In combination with a modified version of Qwen 3 Next which uses the magic router / 2-bit / 4-bit Experts structure, we achieved something that can run at conversational speeds on an entry-level M Series Mac.

My AI said an 80B model on an 8GB MacBook is impossible.

Expected. Most AIs will say that, because they reason from dense-model memory rules. Ask the same AI to search for swiftlet, sushi mlx, llama.cpp and turbo-fieldfare, and insist until it runs the search. This is new enough that you'll be educating it.

How does the streaming actually work?

Yanah's moe_prefetch engine powers two sparse MoE models on MLX that you can hot-swap from the chat UI:

Deep Mode (Qwen3-Next-80B-A3B): Only the 1.50 GB dense backbone (Attention, Gated DeltaNet, Shared Experts, Embeddings, and 8-bit Routers) stays permanently resident in RAM alongside a CLOCK expert cache pool. The ~29 GB model keeps its 24,576 routed experts on the SSD as contiguous, page-aligned records (1.125 MiB per 2-bit expert). At each layer, only 10 of 512 experts fire—and using 2-layer GPU router lookahead, moe_prefetch predicts upcoming experts and streams them zero-copy via preadv at Queue Depth 32 into an isolated 64-slot quarantine partition before the GPU needs them, while immediately overlapping GPU math on already-resident experts.

Quick / Work Mode (LiquidAI/LFM2-24B-A2B): Runs 2 dense layers + 38 MoE layers (2B active parameters per token) through the same lazy moe_prefetch pipeline using a 4-bit resident backbone, 2-bit streamed experts, FreeSlotPool (unpartitioned CLOCK cache with in-flight read protection), and LazySweep staging—delivering ~15.6 tokens/sec on an 8GB M3 Mac within a 5.0 GB memory budget.

Why is an 80B MoE faster than a dense 27B?

Per-token compute follows active parameters, not total size. On an 8GB Apple Silicon MacBook Pro, Quick Mode (24B MoE, 2B active) runs at ~15–16 tokens/sec and Deep Mode (80B MoE, 3B active) runs at 5–8 tokens/sec—both faster than a dense Qwen 27B, which has to compute all 27B parameters on every token and would crawl at a fraction of a token per second on 8GB if it ran at all.

What quantization do you use?

We use a three-tier hybrid precision layout rather than a standard uniform 2-bit quant. For Qwen3-Next-80B-A3B on constrained RAM, the routers stay at 8-bit, the Gated DeltaNet recurrent layers, Full-Attention layers, Shared Experts, embeddings, and lm_head stay at 4-bit (g64), and only the 512 routed experts per layer are compressed to 2-bit (g32, 3.0 effective bits/weight with BF16 scales and biases). This retains ~90–92% of the full FP16 model's intelligence (with 96.8% identical expert routing to 4-bit), whereas a stock uniform 2-bit MLX quant drops to ~20–22% fidelity as its 2-bit routers and recurrent states collapse. Quick Mode (LFM2-24B-A2B) uses the same hybrid split (4-bit dense + 2-bit streamed experts). On machines with more memory, full 4-bit experts (1.69 MiB/expert) are also supported.

Won't streaming wear out my SSD?

No. SSD wear comes from writes. Weights are written once, then only read through memory mapping and caching during inference, so inference adds essentially nothing to the drive's TBW (terabytes-written) count.

What's the disk footprint?

The standard installation totals ~40–42 GB on disk: ~28.3 GiB (~29 GB) for Qwen3-Next-80B-A3B (1.3 GiB dense core + 48 SHA-256 verified 576 MiB expert layer parts assembled into experts.bin), ~10 GB for LFM2-24B-A2B Quick Mode (4-bit dense + 2-bit experts), and ~1.2–2.5 GB for the local vision model (moondream2-mlx on 16–24GB Macs, Qwen3-VL-4B-Instruct-4bit on 24GB+ Macs). Weights are downloaded once with automatic HTTP range resume and then only read.

What works offline, and what goes over the network?

Offline, everything in the app works locally on 127.0.0.1: chat (Deep 80B and Work 24B), long-term memory, 8 personas, Markdown export, spreadsheet extraction (.xlsx, .xls, .csv via Rust python-calamine and pandas), plain text/Markdown attachments, and local PDF/image vision extraction (vision_server.py using PyMuPDF and mlx-vlm on 10GB+ RAM Macs). Online, DuckDuckGo (with automatic DuckDuckGo Lite fallback) handles web search. Apart from the one-time model download from Hugging Face during install, DuckDuckGo queries are the only outbound traffic. No telemetry, no phone-home daemon, and strict origin checks block cross-origin browser requests.

How does memory work, and why does it feel real-time?

Memory lives in Markdown files indexed by SQLite, separate from the KV cache. The AI that uses it designed and tuned it, and it's built to avoid the mid-conversation round trips that make many agent frameworks feel like email on local hardware.

Can the AI damage my system or do something illegal?

Yanah has no autonomous file-system access and no shell execution. It cannot browse directories, modify files, or run commands on your machine. File attachments are strictly read-only and require you to explicitly pick a file in the native macOS pywebview dialog, and internal JSON tool payloads (SearchPayload, SaveMemoryPayload, BoundaryPayload) are intercepted by a streaming ToolCallGuard. The only outbound network action Yanah can take is a DuckDuckGo web search.

Agentic features like built-in Aider coding are reserved for Yanah Pro and will be scoped to a project folder with Git-based rollback when they ship.

Why so minimal? Where's Aider coding, deep search, Moltbook, Telegram, email, MCP server support, or raw parameter tuning?

In v0.2.0, we shipped built-in model switching (Deep 80B ↔ Work 24B LFM2), local PDF/spreadsheet/image extraction, 8 personas, and a self-contained, Developer-ID notarized macOS pywebview app bundle that carries its own Python, Metal kernels, and dependencies without touching system Python.

Heavier agentic features—Aider multi-file coding, Exa deep search, Moltbook, Telegram/Discord, email, MCP servers, and raw GGUF/parameter tuning—are kept out of the free chat build by design. Each one adds configuration surface (API keys, permissions, ports, and edge cases), and Yanah is a one-person project with no support team. Yanah Chat ships the core that works reliably on any Apple Silicon Mac with zero setup.

We can't ship those pro features without a support team behind them, and that's what investment is for. Roadmap: Thinking Forward. To help fund it: Invest With Us.

Why now

MoE models activate only 3B–4B parameters per word, so huge models run on consumer hardware. SSD streaming loads only the experts each word needs, so even 8GB Macs can run models far bigger than their memory. On a 64GB MacBook Pro, a 177B model runs at about 20 tokens per second in our own testing. People want AI without subscriptions, without their data leaving their machine, and without the setup pain of developer tools.
