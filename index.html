Under the hood

Architecture

How Corvus runs huge AI models on a regular Mac: stream only the parts each word needs, keep the rest on your SSD.

Overview

Corvus is a zero-configuration desktop app for Apple Silicon Macs that runs large Mixture-of-Experts (MoE) models locally by streaming weights from the internal SSD instead of holding them all in RAM.

  • Delivery: one .dmg installer with the runtimes and models pre-wired. No CLI, no Swift compilation, no manual model paths, no quantization tuning.
  • Target hardware: Apple Silicon, from base 8GB machines (proof of concept) to 16GB+ Pro/Max machines (production speed).
  • Design priority: zero lag. The goal is a conversation that feels like talking, not like emailing an assistant.

MoE + SSD streaming

Only the experts a token needs are loaded into memory; the rest of the weights stay on the SSD until called.

Why dense models can't do this. A dense model computes every parameter for every token, so all weights must sit in RAM. A dense 26B model would crash an 8GB machine, or stall if forced through an SSD swap file.

Why MoE can. An MoE model activates only a small slice per token. Gemma 4 26B-A4B activates about 4B of its 26B parameters per token; A3B/A4B variants generally run 3B–4B active out of 35B–80B total.

How the streaming works (example: TurboFieldfare running Gemma 4 26B-A4B):

  1. A small shared core (about 1.35 GB) and a 4K KV cache stay resident in unified memory.
  2. The full 14.3 GB weight file stays on the SSD rather than being loaded into RAM.
  3. A custom Swift/Metal engine uses an LFU cache and chunked prefill to page in only the active experts, on demand.
  4. Most experts are cold at any given moment, so paging them from Apple Silicon NVMe costs latency rather than gigabytes of RAM.

Why the storage bus doesn't choke. A full-model swap moves the entire model; expert paging moves only the active slice, and the LFU cache keeps frequently used experts warm.

Request path:

  1. You type a prompt in the desktop app.
  2. The app hands it to the local inference engine (llama.cpp, Metal, or Sushi MLX).
  3. The engine pulls active expert weights through the SSD streaming layer.
  4. Tokens stream back to the app.

Bring your own weights. Power users can drop custom GGUF/MoE files into the local model directory to go beyond the presets.

Memory system

Corvus's long-term memory is separate from the KV cache: plain Markdown files hold the memories, and a local SQLite index makes them fast to retrieve.

  • Ground truth in .md files. Human-readable; you can open, grep, or git diff them.
  • SQLite as the retrieval layer. A derived index for low-latency lookup, without a heavy vector database.
  • Designed by the AI that uses it. The AI built and tested the system, with repeated adjustments until it was satisfied with how it worked.
  • Built for zero lag. Avoids the mid-conversation round trips that make many local agent frameworks feel slow.

Quantization, context, connectivity and coding

Quantization: Q4 standard. Corvus aims for 4-bit quantization, the widely used sweet spot where output quality stays close to the original FP16 weights while files shrink enough for consumer hardware. Aggressive sub-2-bit quantization is avoided because it degrades reasoning.

KV cache. The streaming example keeps a 4K KV cache resident. For long sessions, sliding-window attention or a quantized (e.g. 4-bit) KV cache keeps context from consuming the unified memory pool.

Connectivity has two modes:

  • Online: EXA handles deep, multi-step live web searches.
  • Offline: chat, organization and coding keep working. That includes reasoning and analysis, code generation and debugging, summarizing and outlining documents, brainstorming and planning, data formatting, and working with local files.

Privacy design. Local storage (Markdown + SQLite), no outbound telemetry, no background phone-home daemons. The only network traffic is EXA searches when you're online.

SSD wear. Weights are written once at install and then only read during inference via memory mapping, so they add essentially no write wear.

Coding engine (Aider, built in). Multi-file editing with each change saved as its own Git commit, so any edit can be rolled back. It uses repository mapping to target relevant files rather than the whole disk.

Why a bigger MoE can beat a smaller dense model

Speed tracks the parameters computed per token, not the total size.

  • A dense 27B computes all 27B parameters on every token, which saturates the memory bus.
  • An MoE model wakes only its active experts (about 3B–4B in A3B/A4B designs), so per-token work stays small even when the total runs to 80B–177B.
  • When weights don't fit in RAM, SSD paging adds latency instead of crashing. That's why an 8GB machine can still load an 80B model, just slowly.

What affects your speed

  • Memory: more RAM means more experts stay warm and less paging from the SSD.
  • Chip: Pro and Max chips have much higher memory bandwidth than base chips.
  • Model size: bigger models are smarter but slower on the same hardware.
  • Conversation length: very long conversations use more memory for context, which can slow generation.

Plain English

FAQ (Normies)

Straight answers about Corvus, the private AI that runs on your Mac.

How can an AI run on my laptop? Don't they need giant data centers? The AI has all the information of the internet, right? And it needs giant servers to process that information for chat, right?

It sounds impossible, but an AI doesn't actually store the internet.

Think of it less like an encyclopedia and more like someone who has read an enormous amount and absorbed how language and ideas fit together. When you ask a question, it doesn't look anything up. It writes the answer one word at a time, each time predicting the most sensible next word given everything so far. What it learned is stored as billions of numbers called "parameters," and those fit in a file on your drive.

The giant data centers are mostly for training AIs and serving millions of people at once. Running one for a single person is a far smaller job, and Corvus uses new techniques to make it fit on a regular Mac.

Could the AI go rogue, break my laptop, steal money, and land me in jail?

No. The free version is a chat window: it can't touch your files, open your bank, or do anything on its own. It only replies to what you type.

The paid version includes a coding helper that can edit files in a project you point it at. It can make mistakes, like any assistant, but every change it makes is saved so you can undo it. It has no access to your accounts or passwords and can't act outside that project folder.

Wait, an 80-billion-parameter AI on an 8GB MacBook?

Yes. These models are built from many smaller "experts," and only a few work on any given word. Corvus keeps the rest on your drive and loads experts only when they're needed. On an 8GB Mac a model that size runs slowly, so think of it as a demo, but it really does run. More memory makes it fast.

Is it really private?

Yes. Your chats and memories stay on your computer, and nobody at a company is reading them. Corvus only goes online when you use web search.

Does it work without internet?

Yes. Chatting, writing, summarizing, brainstorming, organizing and coding all work offline. Only live web search needs a connection.

What does it cost?

The basic version is free, with no subscription. A paid tier adds coding tools for developers.

Is it better for the environment?

Your conversations run on your own laptop's power, not in a data center. There are no extra server farms drawing water and electricity just to answer your questions.

I tried LM Studio or Open WebUI and it was painful. How is this different?

Those tools were built by engineers for engineers, and they make you choose models, settings and file formats before anything works. Corvus makes those decisions for you. If you can use Spotify, you can use Corvus: download, open, chat.

I asked ChatGPT/Claude/Gemini and it said this is impossible.

That's expected. This technology is so new that most AIs still go by the old rules. Ask the same AI to search the web for "swiftlet," "sushi mlx," "llama.cpp" and "turbo-fieldfare," and insist until it actually runs the search. You'll be the one teaching it.

Will it wear out my hard drive?

No. What wears out drives is writing new data over and over. Corvus writes the AI to your drive once, then mostly just reads from it, and reading doesn't wear a drive down.

How fast will it be on my Mac?

It depends on how much memory your Mac has and which model you pick. More memory means faster answers. See the Performance page for real examples.

For the techies

FAQ (Devs)

Technical answers on how Corvus runs large MoE models on consumer Apple Silicon.

"To run an 80B model you need at least 64GB of RAM plus headroom for context, right?"

Wrong. Swiftlet, Sushi MLX, llama.cpp and TurboFieldfare can keep most of the weights on the SSD and page in only the active parameters of a sparse MoE model. This isn't voodoo or vaporware; it's bleeding-edge engineering.

My AI said an 80B model on an 8GB MacBook is impossible.

Correct, most will say that, because they reason from dense-model memory rules. Ask the same AI to search for swiftlet, sushi mlx, llama.cpp and turbo-fieldfare, and insist until it runs the search. This is new enough that you'll be educating it.

How does the streaming actually work?

In the TurboFieldfare example (Gemma 4 26B-A4B), about 1.35 GB of shared core plus a 4K KV cache stay resident. The 14.3 GB weight file stays on disk, and a Swift/Metal engine uses an LFU cache and chunked prefill to page in active experts on demand. Because only about 3B–4B parameters are active per token, the bus moves a small slice instead of swapping the whole model. llama.cpp gets a similar effect through --mmap.

Why is a 177B MoE faster than a dense 27B?

Per-token compute follows active parameters, not total size. On a 64GB Apple Silicon MacBook Pro with llama.cpp, the 177B MoE runs at about 20 tokens/sec, faster than dense Qwen 27B, which has to compute all 27B parameters on every token.

* Performance figures are estimates based on internal testing and published benchmarks. Results may vary by Mac model, memory, storage, model choice and conversation length.

What quantization do you use?

Q4 is the standard. It's the widely adopted point where quality stays close to the original FP16 while weights shrink enough for consumer memory. Sub-2-bit quantization is avoided because it degrades reasoning.

Won't streaming wear out my SSD?

No. SSD wear comes from writes. Weights are written once, then only read through memory mapping and caching during inference, so inference adds essentially nothing to the drive's TBW (terabytes-written) count.

What works offline, and what goes over the network?

Online, EXA handles deep multi-step web searches. Offline, everything else keeps working: reasoning, code generation and debugging, summarization, planning, data formatting, and local file work. There's no telemetry and no phone-home daemon; EXA queries are the only outbound traffic.

How does memory work, and why does it feel real-time?

Memory lives in Markdown files indexed by SQLite, separate from the KV cache. The AI that uses it designed and tuned it, and it's built to avoid the mid-conversation round trips that make many agent frameworks feel like email on local hardware. The memory system is proprietary; the glue code is planned to be open source.

Can I use my own models?

Yes. Drop GGUF/MoE files into the local model directory to experiment outside the presets.

Can the AI damage my system or do something illegal?

The Free tier is chat only, with no file-system or shell access. The Pro tier includes a built-in Aider coding engine, and that does carry real risk: it can edit files, run commands like tests and linters, and a bad generation can break code. Here's what limits the damage:

  • It has no root/sudo access and no access to browsers, bank sessions or keys.
  • Every change is its own Git commit, so git reset --hard HEAD~1 reverts it.
  • Repo mapping scopes it to the relevant files.
  • You review the diffs and decide what merges.

Best practice: start from a clean, committed working tree on a feature branch, keep secrets out with .aiderignore, and review the output before it goes anywhere near production.
